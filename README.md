# Playwright 学習プロジェクト
## プロジェクト概要
Playwrightを使用した、ブラウザテスト自動化とCI環境構築の学習プロジェクトです。
GitHub Actionsを用いた自動テストの実行と、VS Codeを活用して実装しています。


## 学習を始めた背景
### 仕様策定から関与できるQAを目指して
テストの実行・検証だけでなく、仕様策定の段階からQAが関与することで、リリース後の手戻りを減らせると考えています。カスタマーサポート出身の経験を活かし、ユーザー視点を仕様に反映させる役割を目指しています。
そのためには開発チームと対等に議論できるスキルが必要と判断し、コードベースのテスト自動化を学ぶことにしました。

### ステップアップとしての学習
MagicPodによるE2Eテスト自動化でヘルススコア96を達成し、JCSQE初級・基本情報技術者試験を取得。
次のステップとして、コードベースのテスト自動化を学ぶことにしました。

### MagicPodで感じた課題の検証
MagicPodの運用を通じて、以下の課題を感じていました。
Playwrightでこれらが解消できるかを検証することも、本プロジェクトの目的の一つです。

- **コスト構造**：ケース数・ステップ数・同時実行数に応じて費用が増加する
- **可読性**：作成者以外がメンテナンスしにくい構造になりやすい
- **ケース管理**：テストケースの量が増えると管理が煩雑になる
- **複雑な分岐**：条件分岐が多いと、作成者自身も解読が困難になる
- **再利用性**：ケース内のステップを別ケースにコピーする際の操作が不便

#### [Codegen・TODOアプリテスト]
Codegenを使い、https://demo.playwright.dev/todomvc/#/ を対象にTODOアプリの基本操作テストを実装

＜テストケース＞
1. TODOアプリにアクセスする
2. TODO項目「買い物リストを作成」を追加する
3. 追加されていることを確認する
4. TODO項目「牛乳を買う」を追加する
5. 追加されていることを確認する
6. 最初のTODO項目を完了状態にする
7. 「1 item left」と表示されることを確認する

- テスト実行に成功
- 記録モードで生成されたコードをそのまま使わず、以下の点を修正した
- 不要な`click()`が記録されていたため削除
- 「牛乳を買う」の要素確認コードを修正した
  - `getByText('牛乳を買う')`はテキストで要素を特定するため、要素の存在確認とテキスト確認が同じ意味になってしまっていた
  - 要素が表示されているかを確認したかったが、記録モードでは意図せずテキスト内容の確認と同じコードが生成されていた
  - 要素の確認は`page.getByTestId('todo-title').nth(1)`で代替できることを確認した

#### [気づき]
- `getByRole`・`getByTestId`・`locator`など要素の取得方法が複数あり、用途によって使い分けが必要
- 記録モードで取れない要素（動的に変わるカウンター表示など）は手書きで補う対応が必要
- 記録モードで生成されたコードは不要なステップ、意図いないステップが混入することがあるため、そのまま使わず見直す習慣が大切
